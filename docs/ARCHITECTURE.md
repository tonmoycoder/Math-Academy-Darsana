# ARCHITECTURE — current build, data, and runtime

**Audience:** anyone changing the build, frontend, backend, or release package.
**Last reviewed:** 2026-10-27 · **Current release line:** v10.3.0 candidate.
**Authority:** `docs/START-HERE.md` is the master brain; this file documents the implemented architecture.

[ASSUMPTION] The project stays framework-less and keeps both the single-file offline build and the Vercel publish build.

[DECISION NEEDED] Do not add another Vercel Function, Neon service, runtime dependency, CDN, or UI system without owner approval.

## 1 · System overview

The repository produces two related outputs:

```text
source HTML/CSS/JS + Markdown + data
                 │
                 ├── python3 _src/build.py
                 │       └── math-academy.html  (self-contained offline landing page)
                 │
                 └── npm run build
                         ├── scripts/pull-content.mjs (Neon → live snapshot)
                         └── python3 _src/build.py --publish
                                 └── dist/ (Vercel-ready site, blog hub, ten articles, assets, SEO files)
```

The landing page is a static HTML document enhanced with inline JavaScript. The hosted build has a static blog and one same-origin function for live business data. There is no framework, bundler, CDN, client-side database SDK, login, or payment flow.

## 3 · Data flow and failure behavior

```text
Neon Postgres ──pull-content.mjs──▶ _src/content/live.json ──build.py──▶ baked HTML baseline
      │                                                               │
      └────────────── /api/content (same-origin Vercel Function) ◀────┘
                             │
                             └── client refresh after paint; silent fallback to baked values
```

1. Neon Postgres is the editable source for per-batch capacity, active batch labels/schedules/fees/fills, next-batch settings, and programme class/mock counts.
2. `_src/content/site.json` is the schema/seed fallback. `_src/content/live.json` is generated by the pull script and must not be hand-edited as a data workflow.
3. `npm run build` pulls and validates Neon before publishing. The pull requires capacity 15, non-empty active batch rows, numeric programme counts, and complete row data. On any validation/connection failure it exits nonzero, leaves `live.json` unchanged, and blocks the build.
4. The single `api/content.js` function provides a public read and admin-token-protected writes. The client fetches it from the same origin after initial paint; if unavailable, the baked baseline remains visible.
5. Capacity is exactly 15 per batch. Dynamic capacity, fills, fees, schedules, monthly class/mock counts, the visible FAQ and JSON-LD must agree with the validated snapshot. Postgres constrains fills to 0–15; the migration reconciles legacy overflow before enforcing the constraint. The library is one test PDF (direct download hosted, data-embedded offline).
6. Only Neon Postgres is enabled. Neon Auth, AI Gateway, Object Storage, Realtime and Neon Functions stay off.

Detailed schema, operations and security: `docs/BACKEND-PLAN.md`, `docs/CONTENT.md`, `docs/SECURITY.md`.

## 5 · Build contract

```bash
npm run build                     # fresh validated Neon pull + publish build
MA_SKIP_PULL=1 python3 _src/build.py --publish  # local-only from a verified snapshot/seed
python3 _src/build.py             # single self-contained HTML (normally attempts a Neon pull)
npm run test:api                  # API + snapshot/data-shape contract tests
```

`dist/` and `math-academy.html` are generated. Never hand-edit them. The publish build clears its generated `dist/blog/` directory before writing the ten current route folders so a stale article cannot survive.

## 6 · Browser behavior and constraints

- JavaScript progressively enhances already-rendered HTML; it does not hydrate a framework view.
- GSAP is vendored and inlined. No external scripts, stylesheets, fonts, or runtime CDN calls are allowed.
- Audio is synthesized with Web Audio, has visible mute controls, attempts autoplay without a prompt, and silently unlocks on interaction if browser policy blocks it. Stored grant data is not itself browser permission.
- The maths-veil treatment is restricted to instructor portraits. No liquid/displacement filter or ripple effect is used.
- The navbar stays sticky, Bengali digits remain readable, and reduced-motion preferences are respected.
- Batch tables scroll within their own wrappers. A rotated decorative marquee may extend past the layout box but is clipped at the document root; it must not create document-level sideways scrolling.

## 7 · Security and privacy boundaries

- No student login, account, payment flow, public booking endpoint, or live student-result service. The schema's `bookings` table is unused by the page/API.
- The CTA/form composes an information-request WhatsApp URL; it does not reserve a seat or post student data to the site.
- `GET /api/content` exposes only public business data. Writes require `ADMIN_TOKEN`; never expose that value to browser code or a package.
- Do not include `.env.local`, Neon credentials, API keys, personal student records, or secrets in `dist/` or release archives.
- Vercel headers and exact deployment checks live in `docs/DEPLOY-VERCEL.md` and `docs/SECURITY.md`.
