## 1 · Current architecture

```text
Neon Postgres
  ├── scripts/pull-content.mjs ──▶ _src/content/live.json ──▶ _src/build.py ──▶ baked HTML fallback
  └── api/content.js ◀──────────── same-origin browser refresh after first paint
```

- **Database:** Neon Postgres.
- **Vercel Functions:** exactly one, `api/content.js`. Helpers stay in `lib/`, `db/`, and `scripts/`; do not add files under `api/` that Vercel might deploy as additional functions.
- **Enabled Neon service:** Postgres only. Keep Neon Auth, AI Gateway, Object Storage, Realtime, and Neon Functions off.
- **Capacity:** exactly 15 students per batch, from the data layer. Seats, fees, and schedules are mutable data and must not be hard-coded into page copy.
- **Fallback:** generated HTML contains the last successfully fetched/seeded snapshot. If Neon is unavailable, the site must remain readable and the build/operator must not describe stale values as current.
- **Visitor accounts:** none. No authentication for public reads; the write path requires the server-side admin token. No student profile or result data is served.
- **Booking:** the public booking form composes a WhatsApp URL; it does not write a booking record. A `bookings` table exists in the schema for possible future use but is not selected by the API and is not part of the current product workflow.

## 3 · Data model

### 3.1 Settings

`settings` stores per-batch capacity, the owner-corrected `team.founded_year` (2022), next-batch labels, pricing/programme configuration, and seeded contact/team settings. The build-time snapshot includes capacity, founding year, next-batch data, pricing and programme counts; batch names, schedules, fees and fills come from active batch rows. The API and pull reject a founding year other than 2022. Do not store private student information in public settings.

### 3.2 Batches

`batches` stores an id, label, class range, schedule, fee, filled count, active state, sort order and WhatsApp message. Capacity is global and owner-approved at exactly 15 students per active batch; no per-batch override is supported. Existing databases may retain a legacy `cap_override` column, but the application ignores it and does not select or update it. Postgres constrains `filled` to 0–15, migration caps legacy values, the API rejects writes above 15, and response shaping clamps any legacy overage as a final display guard. Capacity settings other than 15 are rejected.

### 3.3 Bookings table

A `bookings` table is present in the schema but the current page/API does not submit or read booking records. Do not add personal-data collection without a separate owner-approved privacy/security decision.

## 4 · API contract

| Method | Path | Authorization | Purpose |
|---|---|---|---|
| `GET` | `/api/content` | Public | Read public settings, active batches, computed capacity/seats and update time; cacheable at the edge |
| `GET` | `/api/content?health=1` | Public | Health status only; no-store |
| `POST` | `/api/content` | `Authorization: Bearer $ADMIN_TOKEN` | Patch an allowed batch or setting; no-store |
| `OPTIONS` | `/api/content` | None | CORS/preflight response for the same-origin function contract |
| Other methods | `/api/content` | — | `405` |

Exact request validation, cache headers and response shaping are defined by `api/content.js` and covered in `tests/api.test.mjs`. Do not duplicate the API contract in a second function or client-side database connection.

## 5 · Build and update workflow

```bash
# Pull current Neon content, validate it, then build and publish dist/
npm run build

# Deliberate local-only build from an explicitly reviewed snapshot/seed
MA_SKIP_PULL=1 python3 _src/build.py --publish

# Verify the API contract and data-shape guards
npm run test:api
```

1. Change the value through the approved Neon/database workflow; do not edit rendered HTML or `live.json` manually.
2. Run `npm run build` and confirm the pull log reports capacity 15, founding year 2022, non-empty active batches, filled values 0–15, and a successful snapshot write. If any validation fails or Neon is unavailable, the pull must exit nonzero, leave `live.json` unchanged, and block the build.
3. Audit all rendered readouts: each batch row, meters, remaining seats, header, drawer, callout, booking section, schema and blog content that uses a supported token.
4. Run the API tests, build audit and browser checks.
5. Record which values are owner-confirmed and which remain provisional in `docs/CONTENT.md` / `ai/known-issues.md`.

## 7 · Security and privacy

1. SQL uses parameterized/tagged queries; do not build SQL strings from request fields.
2. `GET` returns public business data only; it never returns `bookings` or student records.
3. `POST` requires a server-side token and validates allow-listed fields. Do not expose the token to page code.
4. Do not add auth, payments, private student profiles, analytics or a second database service without explicit approval.
5. Use same-origin URLs in browser code. The browser must never call `localhost` or a private sandbox service.
6. Keep secrets out of `dist/`, `math-academy.html`, zip archives, logs, screenshots and AI-readable files.
